# 쇼핑몰형 포트폴리오 참고 사이트 분석

작성일: 2026-07-03  
목적: 실제 쇼핑몰 UX를 분석해서 프로젝트 포트폴리오를 쇼핑몰처럼 탐색하고 비교할 수 있는 구조로 전환한다.

## 1. 분석 대상

이번 분석은 실제 운영 중인 쇼핑몰/브랜드몰에서 포트폴리오에 가져올 수 있는 구조만 추렸다. 상품 판매 자체를 따라 하는 것이 아니라, 프로젝트를 상품처럼 탐색하게 만드는 것이 목표다.

| 사이트 | 관찰 포인트 | 포트폴리오 적용 방향 |
| --- | --- | --- |
| [쿠팡](https://www.coupang.com/) | 카테고리, 검색, 장바구니, 찜, 최근 본 상품, 오늘의 발견 | 빠른 탐색, 추천 섹션, 최근 본 프로젝트 |
| [29CM](https://www.29cm.co.kr/) | 취향 기반 기획전, BEST, MY LIKE, SHOPPING BAG, 브랜드/상품 카드 | 프로젝트를 큐레이션 콘텐츠처럼 보여주기 |
| [Nike](https://www.nike.com/) | Featured, Trending, New Arrivals, Bestsellers, 스포츠별 카테고리 | 프로젝트 섹션을 목적/기술/성과별로 분리 |
| [Apple Store](https://www.apple.com/store) | 제품군별 탐색, 구매 이유, 보상판매/배송/개인화 안내 | 프로젝트 상세의 신뢰 요소와 CTA 정리 |
| [Etsy](https://www.etsy.com/) | 검색 중심, 관심사별 점프, 시즌 컬렉션, 좋아요, 개인화 상품 카드 | 태그/관심사 기반 프로젝트 탐색 |
| [UNIQLO](https://www.uniqlo.com/us/en/) / [ZARA](https://www.zara.com/us/) | 성별/카테고리/세일/상품군 중심 내비게이션 | 필터 구조와 카테고리 깊이 참고 |

## 2. 사이트별 관찰

### 2.1 쿠팡

쿠팡은 가장 실용적인 대형 커머스 구조다. 첫 화면에서 카테고리, 검색, 마이페이지, 주문, 찜, 장바구니, 최근 본 상품이 바로 노출된다. 별도 설명 없이도 사용자가 어디서 찾고, 어디에 저장하고, 어디서 다시 이어갈지 알 수 있다.

포트폴리오에 가져올 요소:

- 전체 카테고리: 프로젝트를 `Frontend`, `Backend`, `Full-stack`, `Game`, `Infrastructure`, `AI`처럼 빠르게 나눈다.
- 검색 우선 구조: 프로젝트명, 기술 스택, 문제 상황, 성과 키워드를 한 번에 검색한다.
- 찜 리스트: 관심 프로젝트 저장 또는 비교함으로 변환한다.
- 최근 본 상품: 최근 본 프로젝트로 변환한다.
- 오늘의 발견: 추천 프로젝트, 신규 프로젝트, 인기 프로젝트 섹션으로 변환한다.
- 장바구니: 실제 구매가 아니라 `비교함` 또는 `검토 목록`으로 바꾼다.

주의할 점:

- 쿠팡처럼 정보량이 너무 많으면 포트폴리오의 전문성이 흐려질 수 있다.
- 할인/배송/쿠폰 같은 상업적 요소를 그대로 넣으면 장난스럽게 보일 수 있다.

### 2.2 29CM

29CM은 상품을 단순 목록으로만 보여주지 않고, 기획전과 취향 중심 콘텐츠로 묶는다. 상단에 `Special-Order`, `Showcase`, `PT`, `29Magazine`, `BEST` 같은 메뉴가 있고, 상품 카드에는 할인율, 가격, 무료배송, 신상품, 좋아요 수 같은 판단 정보가 함께 붙는다.

포트폴리오에 가져올 요소:

- Showcase: 대표 프로젝트를 큰 비주얼과 짧은 설명으로 보여준다.
- PT: 프로젝트 문제 해결 과정을 프레젠테이션처럼 구성한다.
- Magazine: 블로그/회고/기술 글과 프로젝트를 연결한다.
- BEST: 조회수, 추천 여부, 성과 기준으로 인기 프로젝트를 보여준다.
- Like: 관심 프로젝트 저장 또는 하이라이트 카운트로 변환한다.
- 상품 카드 보조 정보: 난이도, 기간, 역할, 주요 성과, 사용 기술을 한눈에 표시한다.

주의할 점:

- 29CM식 감성 카피를 과하게 쓰면 개발 포트폴리오의 정보 전달력이 떨어진다.
- 비주얼 중심으로만 가면 실제 구현 내용이 약해 보일 수 있다.

### 2.3 Nike

Nike는 내비게이션을 성별/연령/스포츠/컬렉션 기준으로 나누고, 첫 화면에서는 Featured와 Trending 섹션으로 행동을 유도한다. `New Arrivals`, `Bestsellers`, `Shop All Sale`처럼 사용자의 탐색 의도를 빠르게 나누는 구조가 강하다.

포트폴리오에 가져올 요소:

- Featured: 대표 프로젝트 2~3개를 강하게 노출한다.
- Trending: 최근 개선한 프로젝트, 많이 본 프로젝트, 성과가 좋은 프로젝트를 보여준다.
- New Arrivals: 최근 추가한 프로젝트 또는 최근 리팩터링한 프로젝트.
- Bestsellers: 핵심 역량을 가장 잘 보여주는 프로젝트.
- 스포츠 카테고리: 프로젝트를 기술이 아니라 목적별로도 분류한다. 예: 운영 자동화, 성능 개선, 실시간 처리, 관리자 도구, 데이터 관리.

주의할 점:

- 브랜드몰처럼 hero 이미지만 크고 정보가 적으면 채용/협업 관점에서 설득력이 약하다.
- 프로젝트 카드와 상세에서 기술적 근거를 반드시 같이 제공해야 한다.

### 2.4 Apple Store

Apple Store는 제품을 팔면서도 구매 이유를 같이 제시한다. 제품군 탐색, 보상판매, 결제 방식, 각인, 배송/픽업, 개인화 경험 같은 신뢰 보조 정보가 별도 섹션으로 정리되어 있다.

포트폴리오에 가져올 요소:

- 프로젝트 상세 상단에 핵심 가치 제안 배치: 무엇을 만들었고, 어떤 문제가 해결됐는지.
- 구매 이유 섹션을 `왜 이 프로젝트를 봐야 하는가`로 변환한다.
- 배송/픽업 같은 안내는 `데모 보기`, `GitHub 보기`, `문서 보기`, `API 보기` CTA로 바꾼다.
- 개인화 안내는 `관심 기술 기반 추천` 또는 `관련 프로젝트`로 바꾼다.
- 액세서리 추천은 `연관 기술`, `함께 보면 좋은 글`, `비슷한 문제 해결 사례`로 바꾼다.

주의할 점:

- Apple처럼 미니멀하게만 만들면 프로젝트 수가 적어 보일 수 있다.
- 포트폴리오는 제품 설명보다 문제, 결정, 구현, 결과를 더 분명히 보여줘야 한다.

### 2.5 Etsy

Etsy는 검색과 관심사 기반 큐레이션이 강하다. 첫 화면에서 검색, Gifts, Cart, 관심사, 시즌 컬렉션, 오늘의 딜, 좋아요가 반복적으로 나온다. 상품 카드에는 가격, 할인, 평점, 즐겨찾기가 함께 제공된다.

포트폴리오에 가져올 요소:

- 검색창을 첫 화면 상단에 둔다.
- 관심사 기반 바로가기: `성능`, `인증`, `대시보드`, `배포`, `게임`, `DB`, `API`, `테스트`.
- 시즌 컬렉션은 `최근 집중 작업`, `백엔드 집중`, `프론트엔드 UI`, `인프라 개선` 같은 기획 섹션으로 바꾼다.
- Today's big deals는 `가장 임팩트가 큰 개선` 섹션으로 변환한다.
- Add to Favorites는 관심 프로젝트 저장, 비교함, 공유 링크로 바꾼다.

주의할 점:

- 너무 많은 테마 섹션을 만들면 포트폴리오의 중심 메시지가 흐려진다.
- 개인화 기능은 데이터가 충분해진 뒤 추가하는 것이 좋다.

## 4. 프론트엔드 적용안

### 4.1 첫 화면 구조

첫 화면은 랜딩 페이지가 아니라 쇼핑몰형 탐색 화면이어야 한다. 사용자가 바로 프로젝트를 고르고 비교할 수 있어야 한다.

권장 구조:

1. 상단 고정 헤더
   - 로고 또는 이름
   - 검색창
   - 카테고리 메뉴
   - 관심 프로젝트 아이콘
   - 비교함 아이콘

2. 대표 프로젝트 영역
   - 2~3개의 큰 프로젝트 배너
   - 각 배너에 프로젝트명, 한 줄 성과, 핵심 기술, CTA 배치
   - CTA는 `데모 보기`, `상세 보기`, `GitHub` 중심

3. 카탈로그 섹션
   - 추천 프로젝트
   - 신규 프로젝트
   - 인기 프로젝트
   - 케이스 스터디

4. 빠른 필터
   - Frontend
   - Backend
   - Full-stack
   - Infrastructure
   - Game
   - AI
   - Performance
   - Admin Tool

5. 프로젝트 카드 그리드
   - 상품 목록처럼 비교 가능한 카드
   - 데스크톱은 3~4열, 모바일은 1~2열

### 4.2 프로젝트 카드 구성

카드는 쇼핑몰 상품 카드처럼 짧고 판단 가능한 정보만 담는다.

필수 정보:

- 대표 이미지
- 카탈로그 제목
- 짧은 요약
- 배지: Featured, New, Popular, Case Study
- 프로젝트 유형
- 난이도
- 기간
- 주요 기술 3~5개
- 핵심 성과 1개
- CTA: 상세 보기, 데모, GitHub

예시 카드 정보:

```text
[Featured] 쇼핑몰형 포트폴리오 백엔드
프로젝트 카탈로그, 필터, 태그, 스킬 구조를 쇼핑몰식으로 재설계
Backend · MariaDB · Express · TypeScript
성과: 프로젝트 조회/카탈로그 API 구조 개선
난이도: High · 기간: 2주
```

### 4.3 필터/정렬

쇼핑몰식 필터를 그대로 쓰되 가격/브랜드 대신 개발 판단 기준으로 바꾼다.

필터:

- 프로젝트 유형: Frontend, Backend, Full-stack, Game, Infra
- 기술 스택: React, Next.js, Express, MariaDB, Unity, Docker
- 난이도: Low, Medium, High
- 상태: Completed, In Progress, Archived
- 역할: Solo, Team, Lead, Backend, Frontend
- 성과 유형: 성능 개선, 운영 자동화, UI 개선, DB 설계, 배포 안정화

정렬:

- 추천순
- 최신순
- 인기순
- 난이도 높은순
- 성과 큰순
- 조회 많은순

### 4.4 프로젝트 상세 페이지

상세 페이지는 상품 상세 페이지처럼 상단에서 핵심 판단을 끝내고, 아래로 내려가며 근거를 제공해야 한다.

권장 구조:

1. 상세 상단
   - 이미지 갤러리
   - 프로젝트명
   - 한 줄 가치 제안
   - 배지/상태
   - 핵심 기술
   - CTA: 데모, GitHub, API 문서, 관련 글

2. 핵심 지표
   - 작업 기간
   - 담당 역할
   - 주요 성과
   - 테스트/검증 결과
   - 배포 여부

3. 문제와 해결
   - 문제 상황
   - 선택한 해결 방식
   - 대안과 트레이드오프
   - 구현 결과

4. 기술 상세
   - 아키텍처
   - DB 구조
   - API 흐름
   - 주요 컴포넌트
   - 예외 처리

5. 관련 콘텐츠
   - 관련 프로젝트
   - 관련 블로그 글
   - 사용 기술별 다른 프로젝트

### 4.5 관심 프로젝트/비교함

쇼핑몰의 장바구니를 그대로 쓰지 말고, 포트폴리오에 맞게 비교함으로 바꾼다.

비교 기준:

- 프로젝트명
- 유형
- 기술 스택
- 담당 범위
- 난이도
- 성과
- 배포 링크
- GitHub 링크

1차 구현은 로컬 스토리지로 충분하다. 로그인 기반 저장은 나중에 추가한다.

### 4.6 프론트엔드 우선순위

| 우선순위 | 작업 | 이유 |
| --- | --- | --- |
| 1 | 프로젝트 카탈로그 홈 | 쇼핑몰형 전환의 첫 화면 |
| 1 | 프로젝트 카드 컴포넌트 | 모든 섹션의 기본 단위 |
| 1 | 프로젝트 상세 페이지 개편 | 설득력 핵심 |
| 2 | 검색/필터/정렬 UI | 프로젝트 수가 늘어날수록 필요 |
| 2 | 관심 프로젝트/비교함 | 쇼핑몰 UX를 포트폴리오에 맞게 변환 |
| 3 | 최근 본 프로젝트 | 탐색 편의 기능 |
| 3 | 관련 프로젝트 추천 | 데이터가 쌓인 뒤 강화 |

## 5. 백엔드/API/DB 적용안

### 5.1 현재 스키마 활용 방향

현재 쇼핑몰형 스키마에서는 아래 테이블을 중심으로 프론트엔드 데이터를 만들 수 있다.

| 테이블 | 역할 |
| --- | --- |
| `projects` | 프로젝트 기본 정보, 상태, 공개 여부, 조회수 |
| `project_catalog_profiles` | 쇼핑몰 카드용 제목, 요약, 배지, 가격/난이도 라벨, 우선순위 |
| `project_catalog_sections` | 추천/신규/인기/케이스스터디 같은 카탈로그 섹션 |
| `project_catalog_section_items` | 섹션별 프로젝트 배치 |
| `project_metrics` | 성과 지표 |
| `project_links` | 데모, GitHub, 문서, API 링크 |
| `project_images` | 카드 이미지, 상세 이미지, 갤러리 |
| `project_tags` / `tags` | 관심사/주제 기반 탐색 |
| `project_skills` / `skills` | 기술 스택 기반 필터 |

### 5.2 공개 API 설계

기본 공개 API:

```http
GET /public/projects/catalog
GET /public/projects
GET /public/projects/:slug
POST /public/projects/:slug/view
```

`GET /public/projects/catalog`

- 목적: 쇼핑몰 홈의 섹션 데이터를 한 번에 제공
- 반환: 추천 프로젝트, 신규 프로젝트, 인기 프로젝트, 케이스 스터디
- 프론트 사용 위치: 홈 화면 카탈로그 섹션

`GET /public/projects`

- 목적: 프로젝트 목록, 검색, 필터, 정렬
- 쿼리 예시:

```http
GET /public/projects?search=database&type=backend&skills=mariadb,express&project_status=completed&sort=popular&page=1&limit=12
```

- 지원하면 좋은 필터:
  - `search`
  - `type`
  - `skills`
  - `tags`
  - `difficulty`
  - `project_status`
  - `featured`
  - `sort`
  - `page`
  - `limit`

`GET /public/projects/:slug`

- 목적: 프로젝트 상세
- 포함 데이터:
  - 기본 프로젝트 정보
  - 카탈로그 프로필
  - 이미지 갤러리
  - 링크
  - 성과 지표
  - 기술 스택
  - 태그
  - 상세 섹션
  - 관련 프로젝트 후보

`POST /public/projects/:slug/view`

- 목적: 조회수 증가
- 최근 본 프로젝트는 백엔드 저장보다 프론트 로컬 스토리지 우선

### 5.4 추천/섹션 로직

초기에는 복잡한 추천 알고리즘보다 명시적 섹션 배치가 낫다.

추천 우선순위:

1. `project_catalog_section_items`에 직접 등록된 프로젝트
2. 없으면 `project_catalog_profiles.catalog_priority` 기준
3. 그래도 없으면 `projects.is_featured`, `view_count`, `published_at` 기준

섹션 종류:

- `featured`: 대표 프로젝트
- `new_arrivals`: 최근 추가/개선 프로젝트
- `popular`: 조회수 높은 프로젝트
- `case_study`: 상세 설명이 좋은 프로젝트
- `backend_focus`: 백엔드 중심 프로젝트
- `frontend_focus`: UI/인터랙션 중심 프로젝트

### 5.5 검색 설계

검색은 단순 제목 검색보다 넓게 잡아야 한다.

검색 대상:

- `projects.title`
- `projects.summary`
- `projects.content_text`
- `project_catalog_profiles.catalog_title`
- `project_catalog_profiles.catalog_summary`
- `project_catalog_profiles.impact_summary`
- `tags.name`
- `skills.name`

검색 결과 카드에는 검색어가 왜 매칭됐는지 힌트를 주면 좋다.

예:

```text
"MariaDB" 검색 결과
- 쇼핑몰형 포트폴리오 백엔드
  매칭: 기술 스택 MariaDB, DB 스키마 재설계
```

### 5.6 백엔드 우선순위

| 우선순위 | 작업 | 이유 |
| --- | --- | --- |
| 1 | `/public/projects/catalog` 안정화 | 홈 화면 핵심 데이터 |
| 1 | `/public/projects` 필터/정렬 확정 | 목록 탐색 핵심 |
| 1 | `/public/projects/:slug` 상세 응답 확정 | 프로젝트 설득력 핵심 |
| 2 | 관리자 프로젝트 등록 payload 정리 | 콘텐츠 운영 효율 |
| 2 | 섹션 관리 API | 추천/신규/인기 섹션 운영 |
| 3 | 관련 프로젝트 API | 상세 페이지 체류 증가 |
| 3 | 조회 기반 추천 | 데이터가 쌓인 뒤 적용 |

## 6. 그대로 가져오면 안 되는 요소

쇼핑몰의 모든 요소가 포트폴리오에 맞지는 않는다.

피해야 할 것:

- 실제 가격처럼 보이는 정보
- 할인율/쿠폰/배송 문구를 그대로 흉내 내는 표현
- 장바구니라는 단어를 그대로 쓰는 것
- 과한 광고 배너
- 프로젝트보다 배지가 더 눈에 띄는 카드
- 상세 페이지에서 기술 근거 없이 감성 문구만 반복하는 구조

대신 써야 할 것:

- 가격 -> 난이도, 기여도, 임팩트
- 할인 -> 개선 폭, 성능 향상, 작업 전후 차이
- 배송 -> 데모 접근성, 문서 접근성, API 접근성
- 리뷰 -> 회고, 테스트 결과, 운영 지표
- 장바구니 -> 비교함, 관심 프로젝트

## 8. 다음 작업 제안

권장 순서:

1. 프론트엔드에서 프로젝트 카드 컴포넌트부터 만든다.
2. `/public/projects/catalog` 응답을 기준으로 홈 카탈로그 화면을 만든다.
3. 프로젝트 상세 페이지를 상품 상세처럼 개편한다.
4. 목록 페이지에 검색/필터/정렬을 붙인다.
5. 로컬 스토리지 기반 관심 프로젝트/비교함을 추가한다.
6. 관리자 화면에서 카탈로그 프로필과 섹션 배치를 관리할 수 있게 한다.

결론적으로 이 방향은 괜찮다. 다만 쇼핑몰의 외형만 따라가면 가벼워 보일 수 있으므로, 카드와 상세 페이지 안에 `문제`, `해결`, `기술 선택`, `성과`, `검증`을 반드시 같이 넣어야 한다. 쇼핑몰 UX는 탐색과 비교를 쉽게 만드는 틀로만 사용하고, 설득은 개발 포트폴리오의 근거로 해야 한다.
